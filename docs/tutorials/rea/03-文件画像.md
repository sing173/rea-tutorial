## 第 3 章 文件画像：结构、布局与构建来源

> 状态：已审阅（2026-10-27 按 REA 6.8.0 + Go 1.27.3 实测校对；来源见 9）。
> 环境：容器 `rea-ghidra:6.8.0`（REA 6.8.0 + binutils 2.40 + file 5.44）；样本 `/root/weknora-lite/WeKnora-Lite`。
> 运行方式：REA 命令在容器内执行，例如
> `docker run --rm -it -v /root/weknora-lite:/root/weknora-lite:ro rea-ghidra:6.8.0 bash`；`go version -m` 在构建机（Go 1.27.3）执行。宿主机不再安装 REA。

本章在反编译之前先为样本建立一份可引用的“文件画像”：确认它是谁（路径、大小、SHA-256），里面有什么（文件容器、节区/段、notes，术语见第 0 章 5），以及它是怎么构建的（Go 版本、依赖、构建参数）。读完应得到一张组件地图，知道第 4 章该反编译哪些函数；全程只读文件，不执行目标。

### 1 定义问题与范围

面对一个未知二进制，第一步是明确要回答的问题，而不是立即反编译：

1. 文件是什么（格式、架构、链接方式）
2. 容器结构（节区、段、notes）
3. 构建来源（Go buildinfo、依赖、构建参数）
4. 行为（第 5 章以后）

本章覆盖问题 1–3，函数逻辑留给第 4 章。第 3、4 章的分析对象是文件本身：读取字节、建立结构、提取构建信息，再进入函数级分析；目标进程不会被执行。Ghidra 作为分析引擎运行，但它只导入和分析文件字节，运行时行为留到第 5 章以后验证。

工作流与本章小节对应：

| 步骤 | 做什么 | 本章小节 | 产出 |
|---|---|---|---|
| 0 | 定义问题与范围 | 1 | 要回答的问题、数据边界 |
| 1 | 样本身份与摘要 | 2 | 路径、大小、SHA-256、格式 |
| 2 | 容器/结构盘点 | 3 | 容器图、结构表、工具选择 |
| 3 | 文件布局与表级事实 | 4 | 节区/段/入口、反例边界 |
| 4 | 构建来源与依赖 | 5 | Go 版本、依赖与构建参数 |
| 5 | 组件地图与目标筛选 | 6 | 高价值组件清单 |
| 6 | 证据边界 | 7 | observed/inferred/unknown |
| 7 | 练习与复现 | 8 | 可重放结果 |

> 新手建议按 0→7 顺序读；每一步都保留 `evidence_id` 或命令输出，下一步只使用上一步确认过的事实。

### 2 样本身份与摘要

分析对象必须先绑定字节身份：路径、大小、SHA-256 和格式。后续所有 Evidence、比较和报告都引用这个身份，避免“分析的是哪份文件”说不清。

#### 2.1 取样本并记录摘要

样本是在构建机上自建的 WeKnora Lite 桌面端二进制（Wails + WebKit + SQLite/FTS5）。把它取到分析机：

```bash
mkdir -p /root/weknora-lite
scp root@<build-host>:"/root/weknora-lite-linux/WeKnora Lite" /root/weknora-lite/WeKnora-Lite
ls -l /root/weknora-lite/WeKnora-Lite
sha256sum /root/weknora-lite/WeKnora-Lite
file /root/weknora-lite/WeKnora-Lite
```

本次实测：

```text
279195936  /root/weknora-lite/WeKnora-Lite
f748a5972aa145684ba0293854f7a1493f765ee7d0673105cd7ae175e267aa16
ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically linked,
interpreter /lib64/ld-linux-x86-64.so.2,
BuildID[sha1]=e8137e29d6539683b35fb17178246ae111cb3318,
for GNU/Linux 3.2.0, stripped
```

**名称解析**

| 名称 | 含义 |
|---|---|
| ELF | Linux 的可执行/对象文件格式；`ELF64` 表示 64 位。 |
| stripped | 符号表被移除，函数名/调试信息减少。 |
| dynamic / interpreter | 依赖动态链接器加载共享库；`/lib64/ld-linux-x86-64.so.2` 是解释器。 |
| BuildID | 链接器写入的构建标识，便于把崩溃/调试信息与二进制对上。 |
| EXEC / PIE | 本例 `file` 输出 `executable`、`readelf` 的 `Type: EXEC`，表示固定装载地址（基址 0x400000），不是 PIE。 |

> `file` 的 “executable” 只描述格式与链接方式，不表示“能安全运行”。

### 3 容器与结构盘点

文件身份确定后，先确认“文件里有哪些容器/子产物、有哪些结构表”，并选择读得动的工具。这里的“容器”指文件/打包容器（ELF、APK、ASAR、PCK 等），不是 Docker 容器；REA 的 artifact 图负责容器层，ELF 布局则由 layout/readelf 负责，两者的读取预算不同。

以本次样本为例：

- **容器层**：普通 ELF 可执行文件，不是 APK/ASAR/PCK 这类容器；artifact 图只记录根文件（`format=elf`）。
- **结构表**：ELF header、program header table（14 个段）、section header table（42 项，41 个有名节）。
- **节区示例**：`.text`（代码）、`.rodata`（只读数据）、`.data`/`.bss`（可写数据）；Go 特有的 `.gopclntab`/`.go.buildinfo`/`.go.module`；动态链接的 `.interp`/`.dynamic`/`.dynsym`/`.rela.*`；构建标识 `.note.gnu.build-id`。

盘点时先列出这些“有什么”，再决定用哪种工具。

先从 artifact 图开始：

```bash
rea inspect-artifact /root/weknora-lite/WeKnora-Lite --json > /tmp/weknora-lite-artifact.json
jq '{evidence_id, subject, provider, confidence, limitations}' /tmp/weknora-lite-artifact.json
```

> 这两条命令都在 `rea-ghidra` 容器内执行（见顶部运行方式）；`/tmp` 是容器内临时目录，退出容器即消失。需要保留时，用可写挂载（去掉 `:ro`）并把输出写到 `/root/weknora-lite/` 下。

本次实测（节选）：

```json
{
  "evidence_id": "ev_df090734feca3d2820e91b3195363fba0880441a09e81a158c468fa469d24885",
  "subject": {
    "name": "WeKnora-Lite",
    "digest": { "sha256": "f748a5972aa145684ba0293854f7a1493f765ee7d0673105cd7ae175e267aa16" },
    "format": "elf",
    "architecture": null
  },
  "provider": { "id": "rea-artifact-graph", "name": "REA safe artifact graph provider", "version": "1" },
  "confidence": "observed",
  "limitations": [
    "Inspection derives bounded static hypotheses and next probes; it does not execute the artifact or claim format-specific semantics.",
    "Inventory covers root bytes only; child container entries were not examined."
  ]
}
```

关键点：

- 279 MB 文件可以直接跑（**不受** `inspect-go-binary` 的 256 MiB 限制）。
- `provider` 是 `rea-artifact-graph`：它负责“产物图/容器”，不是 ELF 语义。
- `architecture` 为 `null` 不是失败：artifact 图没有解析 ELF header 的 machine 字段。

**名称解析**

| 名称 | 含义 |
|---|---|
| artifact graph | REA 的产物图：根文件 + 嵌套容器/条目的安全盘点。 |
| evidence_id | 本次观察的 Evidence 标识，后续比较/报告引用它。 |
| confidence | 事实等级（observed/derived/inferred）。 |

容器层确认后，再看结构表该用哪个工具。各工具的读取预算不同：

| 要回答的问题 | 工具 | 实测限制 | 本次结果 |
|---|---|---|---|
| 格式/摘要/容器图 | `inspect-artifact` | 279 MB 可读 | 成功，`architecture=null` |
| ELF 节区/段/符号/缓解 | `inspect-binary-layout`（本项目已启用） | 完整文件需调 `REA_PWNTOOLS_MAX_INPUT_BYTES`（本镜像 512 MiB） | 10 s，Evidence `ev_05678e09…` |
| ELF notes / build-id | `inspect-elf-notes` | 默认 64 MiB，`--max-file-bytes` 可调到 512 MiB | 调大后成功（6 tables / 8 entries，build-id 可读） |
| Go buildinfo | `inspect-go-binary`（≤256 MiB） | 固定 256 MiB，无运行时开关 | 279 MB 超限；改用 `go version -m`（见 5.3） |

> `inspect-binary-layout` 的作用是“文件级布局”：节区/段、符号表、重定位、静态链接名、缓解标志（NX/PIE/RELRO 等），以及文件偏移与链接地址的对应；不反汇编、不执行、不给运行时基址。它和 `readelf` 的区别是输出结构化 Evidence；本镜像已把 `REA_PWNTOOLS_MAX_INPUT_BYTES` 调到 512 MiB。
>
> 通用情况下它是可选项；**本项目因多 agent 交接需要结构化 Evidence，镜像默认启用**。对完整 WeKnora-Lite 实测 **10 秒**：布局包含 42 个节、14 个段，符号与重定位数量很大（本次约 6.3 万符号、6 千重定位），Evidence `ev_05678e09…`。结构化 Evidence 的适用场景见第 8 章 2.1；MCP 下完整结果可能超过 10 MiB 响应预算，用保留视图 summary 或 CLI JSON。
>
> Ghidra 与 `readelf` 的分工：Ghidra 是“装载后的程序模型”，可能对 PIE rebase、合并/忽略非装载节区，并按分析结果创建函数；**表级事实以 `readelf` 为准，函数级语义以 Ghidra 为准**，两边坐标不要混用。

失败原文（失败也是证据）：

```json
{"code":"resource_constraint","category":"resource_constraint",
 "message":"Selected artifact exceeds 67108864 bytes: /root/weknora-lite/WeKnora-Lite",
 "details":{"operation":"inspect_elf_notes","resource":"file-size",
            "reported_limits":{"max_file_bytes":67108864,"max_entries":32}}}
```

> 这是 `inspect-elf-notes` 默认 64 MiB 限制下的报错，4.3 会调大 `--max-file-bytes` 重试。

> 选工具前先看它的输入预算；大文件不是“所有工具都能读”。

容器与工具确认后，下一步读取文件布局与 notes。

### 4 文件布局与表级事实

容器的结构确认后，先用 `readelf` 读表级事实，再用 `inspect-binary-layout`/`inspect-elf-notes` 得到结构化 Evidence。这一步的结论用于第 4 章判断 Ghidra 的装载模型与地址坐标。

#### 4.1 用 binutils 交叉验证

REA 不重复实现 binutils；示例容器里带了 `readelf`，用来交叉验证：

```bash
readelf -hW /root/weknora-lite/WeKnora-Lite | head -12
readelf -SW /root/weknora-lite/WeKnora-Lite | head -8
readelf -SW /root/weknora-lite/WeKnora-Lite \
  | sed -n 's/^ *\[ *[0-9]*\] *\([^ ]*\).*/\1/p' | grep -c '^\.'
```

本次实测：

- `Type: EXEC`、`Machine: Advanced Micro Devices X86-64`、`Entry point address: 0xf0e8e0`
- `There are 42 section headers`（含 0 号 NULL），41 个有名字的节
- `.interp` 位于 `0x400350`

**名称解析**

| 名称 | 含义 |
|---|---|
| section header table | 节区表：每个节的名称、类型、地址、偏移、大小。 |
| program header | 段表：装载器使用的映射描述（只读/可执行/可写）。 |
| entry point | 进程启动后第一条指令的虚拟地址。 |

#### 4.2 结构化布局（`inspect-binary-layout`）

`readelf` 适合人工交叉验证；需要结构化 Evidence 时，用 `inspect-binary-layout` 读取同一份文件：

```bash
rea inspect-binary-layout /root/weknora-lite/WeKnora-Lite --json > /root/weknora-lite/WeKnora-Lite-layout-full.json
```

本次实测（节选）：

```text
image_type: ET_EXEC
entry_point: 0xf0e8e0（linked-virtual-address；runtime_load_base unknown）
linkage.needed_libraries: 13 个（libm、libwebkit2gtk-4.0.so.37、libgtk-3.so.0、libgdk-3.so.0、…）
mitigations: position_independent=false, nx_indicator=true,
             executable_stack_indicator=false, stack_canary_indicator=true,
             relro=Partial（evidence_kind=inferred）
sections: 42  segments: 14  symbols: 约 6.3 万  relocations: 约 6 千
Evidence: ev_05678e09…
```

读结果时注意：

- `entry_point` 是**链接地址**，不是运行时地址；`runtime_load_base` 未知。
- `mitigations` 是静态推断（inferred），不证明运行时防护生效。
- `needed_libraries` 是动态链接依赖，能解释桌面端为什么链接 WebKitGTK/GTK。
- 符号/重定位数量大，按需查询，不逐条阅读。

#### 4.3 notes 与 build-id（`inspect-elf-notes`）

ELF note 是 ELF 中的一类元数据表（`PT_NOTE` 程序头或 `SHT_NOTE` 节区），由 owner/type/descriptor 组成；常见的有 GNU build-id、ABI tag 与 Go 自己的 note。

`inspect-elf-notes` 读取 `PT_NOTE`/`SHT_NOTE`，给出 build-id、ABI tag 和 Go 自己的 note。默认上限 64 MiB，可用 `--max-file-bytes` 调大（最高 512 MiB）：

```bash
rea inspect-elf-notes /root/weknora-lite/WeKnora-Lite \
  --max-file-bytes 300000000 --max-entries 64 --json
```

本次实测（节选）：

- Evidence `ev_5bb7e834…`；6 个 note 表、8 个条目，覆盖状态 `complete`。
- GNU build-id：`e8137e29d6539683b35fb17178246ae111cb3318`（与 `file` 输出一致）。
- GNU ABI tag：`linux 3.2.0`。
- 还有 Go 自己的 note（owner `Go`，type 4）。

注意：`PT_NOTE` 与 `SHT_NOTE` 独立检查，同一文件范围可能出现两次；缺少 note 表只表示“没有声明”，不等于从未携带。

结构确认后，下一步从 buildinfo 读取构建来源与依赖。

### 5 构建来源与依赖

这一步从二进制内嵌的 buildinfo 读取“谁、用什么工具链、依赖了什么”。先明确 buildinfo 的字段和适用范围，再处理 256 MiB 的固定预算，最后给出两条读取路径：完整文件用 `go version -m`，≤256 MiB 或需要结构化 Evidence 时用 `inspect-go-binary`。

#### 5.1 为什么读 Go 元数据

Go 把构建信息（编译器版本、主模块、依赖、构建参数）直接嵌进二进制。读取这些字节不需要反编译器。

先拿到“构建来源 + 组件地图”，再决定反编译哪些函数，比直接冲进 `.text` 更有效。

字段（来自 `go-binaries.md`）：

| 字段 | 含义 |
|---|---|
| `go_version` | 编译器字符串；保留原始 UTF-8，不强制语义化。 |
| `module.main` | 主模块 path/version/checksum/replacement。 |
| `module.dependencies` | 依赖模块及原始顺序。 |
| `module.settings` | `GOOS`/`GOARCH`/`CGO_ENABLED`/`-tags`/`-ldflags` 等，保留重复键。 |
| `module.complete` | module 文本是否逐行解析完整；不代表依赖清单完整。 |

**名称解析**

| 名称 | 含义 |
|---|---|
| buildinfo | Go 二进制内嵌的构建元数据。 |
| module / replacement | Go 模块路径/版本；replacement 是 `replace` 指令的替换源。 |
| ldflags | 链接器参数，常用 `-X` 注入版本/commit。 |
| CGO | Go 调用 C 的机制；`CGO_ENABLED=1` 表示启用。 |
| pclntab | Go 的 PC-行号表，保存函数/行号映射。 |

**适用范围**：只对 Go 编译出的二进制有效（ELF/PE/Mach-O 容器均可）。非 Go 二进制没有 buildinfo，字段为空/unknown，**不能据此断定“不是 Go”**；Rust/.NET/通用二进制改用 `inspect-rust-binary`、`inspect-managed-*`、`inspect-binary-layout` 或 Ghidra。

#### 5.2 输入预算：256 MiB 固定上限

`inspect-go-binary` 的输入上限是 **256 MiB（268,435,456 B）**，6.8.0 **没有运行时开关**。对完整样本直接跑会得到：

```json
{"code":"resource_constraint","category":"resource_constraint",
 "message":"Selected artifact exceeds 268435456 bytes: /root/weknora-lite/WeKnora-Lite",
 "details":{"operation":"inspect_go_binary","reported_limits":{"maximum_input_bytes":268435456}},
 "remediation":{"action":"... Do not truncate required bytes; retrying the unchanged oversized input will fail again."}}
```

明确规则：

1. **超过 256 MiB 不要用 `inspect-go-binary`**。
2. **超过 256 MiB 用 `go version -m` 读取原始文件**（见 5.3）。

为什么是 256 MiB：读取器的固定资源预算——选中文件与 header 搜索各 256 MiB、内嵌字符串 1 MiB、结构化表 16 MiB、报告 8 MiB；大文件会让扫描的内存/时间不可控。6.8.0 没有 `--max-file-bytes` 或环境变量；可调的是 `inspect-binary-layout` 的 `REA_PWNTOOLS_MAX_INPUT_BYTES` 和 `inspect-elf-notes` 的 `--max-file-bytes`。改 REA 源码不推荐。

#### 5.3 读取完整文件：`go version -m`

在构建机（有 Go 1.27.3）上：

```bash
cd /root/weknora-lite-linux
go version -m "WeKnora Lite" > /root/weknora-lite-go-version-m.txt
```

在构建机上生成后拷回分析机：

```bash
scp root@<build-host>:/root/weknora-lite-go-version-m.txt \
  /root/weknora-lite/WeKnora-Lite-go-version-m.txt
```

本次实测（**0.005 秒**，输出约 330 行，含 312 条依赖记录）：

```text
WeKnora Lite: go1.27.3
	path	github.com/Tencent/WeKnora/cmd/desktop
	mod	github.com/Tencent/WeKnora	(devel)
	dep	...（依赖清单较长，略）
	build	-buildmode=exe
	build	-compiler=gc
	build	-ldflags="... Edition=lite ... CommitID=97d7f0a ..."
	build	-tags=desktop,sqlite_fts5,wv2runtime.download,production
	build	CGO_ENABLED=1
	build	GOARCH=amd64
	build	GOOS=linux
```

要点：

- `path` 是主包 `cmd/desktop`，比模块路径更具体；`mod` 才是模块 `github.com/Tencent/WeKnora`。
- `dep` 行包含模块、版本和 `h1:` 校验和；缺失的校验和为 null。
- `build` 行是构建设置；`-ldflags` 里常注入版本/commit。
- `go version -m` 不加载整个 279 MB，只按 ELF 表定位 buildinfo。
- 输出不是 REA Evidence；记录**命令、二进制 SHA-256、输出文件**，作为 observed 证据。

#### 5.4 结构化 Evidence：`inspect-go-binary`

- 文件 **≤256 MiB** 时：它是 REA 原生路径，返回结构化 Evidence 和 `evidence_id`。
- 适合用小 Go 二进制练手（自己 `go build` 一个 hello），观察字段和限制。
- 对 279 MB 的 WeKnora Lite：**不用**，改用 5.3。

两种读法的区别：

| 维度 | `go version -m`（原始文件） | `inspect-go-binary`（≤256 MiB） |
|---|---|---|
| 对象 | 原始 279 MB 文件 | 原始文件（≤256 MiB） |
| 输出 | 文本：`path`/`mod`/`dep`/`build` | 结构化 Evidence：`evidence_id`、精确偏移、base64、`complete`、limitations |
| 依赖/设置 | 完整依赖与构建设置（含 checksum） | 同上，另有精确文件偏移与原始字节 |
| 交接 | 无 `evidence_id`；记录命令 + 原始 SHA + 输出文件 | 可引用、可比较、可导出 |
| 限制 | 需 Go 工具链；只读 buildinfo | 固定 256 MiB；结构必须合法 |

> 结论应一致（同一份 buildinfo）；若不一致，先确认是否同一文件（SHA-256）。

### 6 组件地图与目标筛选

构建信息拿到后，把依赖清单转成“去哪里找函数”的地图，为第 4 章挑选目标做准备。这里只使用构建期事实，不推断运行时实际启用了哪些后端。

#### 6.1 依赖分类与组件地图

### 7 证据边界

每一步都要记录事实等级、覆盖与限制。以下边界适用于本章所有工具，也是多 agent 交接时必须随结论一起交付的内容。

#### 7.1 能证明什么

- 文件格式、SHA-256、大小、容器图。
- 节区/notes（在工具限制内）。
- Go buildinfo 与依赖清单。

#### 7.2 不能证明什么

- 函数逻辑、运行时行为、依赖真实性、安全性、覆盖完整。
- `confidence` 与 `limitations` 必须一起读：`observed` 只说明“这次读取观察到了”，不说明“覆盖完整”。
- 依赖清单 ≠ 运行时依赖图（可能有条件编译/动态加载）。
- `go version -m` 的输出不证明编译器身份、依赖真实性或运行行为。
- `(devel)` 表示主模块是本地构建（无版本号）。

### 8 练习与复现

1. 对 `WeKnora-Lite` 跑 `file` 和 `sha256sum`。
   预期：`ELF 64-bit LSB executable ... stripped`；摘要 `f748a597...`；大小 `279,195,936 B`。
2. 跑 `inspect-artifact`，用 `jq` 取 `provider.id`、`subject.architecture`、`confidence`。
   预期：`rea-artifact-graph`、`null`、`observed`；`evidence_id` 可引用。
3. 对 `/usr/bin/ls` 跑 `inspect-elf-notes`，再对 `WeKnora-Lite` 跑一次。
   预期：前者成功（返回 notes/tables），后者 `resource_constraint`（64 MiB）。
4. 用 `readelf -SW` 数有名字的节区。
   预期（binutils 2.40、本例）：41。
5. 在构建机上对完整 `WeKnora Lite` 跑 `go version -m`。
   预期：依赖记录 312 条、`build` 记录 13 条；`path=github.com/Tencent/WeKnora/cmd/desktop`。
6. （可选）对完整 `WeKnora-Lite` 跑 `inspect-binary-layout`。
   预期：42 个节、14 个段；符号约 6.3 万、重定位约 6 千，Evidence `ev_05678e09…`。
7. 写 2 条 observed、2 条 unknown（例如“运行时模块初始化顺序”“`Edition=lite` 下哪些依赖实际被调用”），并各附一个 `evidence_id` 或命令输出。
