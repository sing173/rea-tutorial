## 第 4 章 函数级分析：主流流程、全量与证据边界

> 状态：已审阅（2026-10-29 按 Ghidra 12.1.4 + Go 1.26.10/1.27.3 实测校对，并对照 Ghidra/REA/GoReSym 社区流程；来源见 10）。
> 环境：`rea-ghidra:6.8.0` 容器（Ghidra 12.1.4 + Temurin JDK 21）；以下命令在容器内执行，例如
> `docker run --rm -it -v /root/weknora-lite:/root/weknora-lite:ro rea-ghidra:6.8.0 bash`。
> 样本：Go 1.27.3 原始构建 `/root/weknora-lite/WeKnora-Lite`；Go 1.26.10 官方基线 `/root/weknora-lite-go126/WeKnora-Lite`。

本章承接第 3 章的组件地图，按当前主流的函数级逆向流程走一遍：先做全量自动分析，再恢复函数身份、选目标、反编译、看类型/接口，最后写清证据边界。输出是函数级 observed/inferred/unknown 和可引用的 Evidence；目标进程不执行，运行时验证见第 5 章。

### 1 定义问题与范围

函数级分析不是“把 279 MB 全部反编译一遍”，而是按阶段回答：

1. **行为**：这个函数做什么？控制流、错误码、字符串常量是什么？
2. **关系**：它调用谁、谁调用它？直接调用和接口分派分别是什么？
3. **身份**：函数名、边界、类型/签名从哪里来？Go 版本是否被引擎支持？
4. **全量边界**：全量分析能否完成？能恢复多少？受阻时如何降级？
5. **证据**：哪些是 observed、哪些是 inferred、哪些仍是 unknown？

本章只读文件字节；Ghidra 作为分析引擎导入/分析字节，不运行目标。运行时行为（实际接口实现、分支值、数据库写入）留到第 5 章以后。

#### 1.1 主流流程与本章对应

社区工具的工作流大体一致，只是自动化程度不同：

| 阶段 | 社区常见做法 | 本章小节 | 产出 |
|---|---|---|---|
| 0 样本/引擎 | 确认 SHA/格式，准备 Ghidra/IDA/Binary Ninja | 2 | 样本身份、provider healthy |
| 1 全量自动分析 | Ghidra 导入默认 Auto Analyze；REA `analyze`/`binary_overview`；IDA/BN 加载后自动分析 | 3 | 函数/字符串/段/引用 |
| 2 函数识别/符号恢复 | pclntab、RTTI、FLIRT/签名、GoReSym | 4 | 函数名/边界/真实地址 |
| 3 目标选择/triage | 入口、导入、字符串、xref、调用图；不要逐个函数硬读 | 5 | 高价值函数清单 |
| 4 函数级反编译 | decompile + 汇编对照；注释、重命名、类型 | 6 | 伪代码、调用者/被调用者 |
| 5 类型/接口 | RTTI、itab + wrapper；必要时动态确认 | 7 | 类型/接口目标 |
| 6 动态验证 | 调试器/插桩确认实际实现、分支和值 | 8.1 | 运行时 observed |
| 7 证据/报告 | 地址、函数、字符串、置信度、复现步骤、Evidence | 8.2–8.7 | Evidence/报告 |
| 复现 | 练习 | 9 | 可重放结果 |

> **全量是默认的第一遍**：Ghidra 在导入/新增程序时会自动跑 Auto Analysis；REA 的 `analyze`/`function` 也会先完成完整导入+分析。只有全量在当前对象/引擎上无法完成时，才用 6.4 的定向后备。大型/混淆/恶意样本常做目标驱动的 triage，那是全量受阻时的合法变体，不是正常目标的替代路径。

### 2 样本、目标与引擎

先把分析对象和引擎固定下来。样本的格式、节区、构建来源已在第 3 章确认；本章只补函数级分析需要的地址和工具状态。

#### 2.1 两个样本

本章使用同一源码（`Tencent/WeKnora` @ `97d7f0a`）的两个构建：

- **Go 1.27.3 原始构建**：`/root/weknora-lite/WeKnora-Lite`，279,195,936 B，SHA-256 `f748a5972aa145684ba0293854f7a1493f765ee7d0673105cd7ae175e267aa16`；`moduledata.text=0xf0ea00`；`AutoSetup=0x5702e60–0x57037c0`（0x960 B）。
- **Go 1.26.10 官方基线（1.26 补丁版）**：`/root/weknora-lite-go126/WeKnora-Lite`，283,770,464 B，SHA-256 `296f0611d7432597de7f8320aa16c48a6b5bbc36e4545d71a047f8a5b90cc5da`；`moduledata.text=0xf0da00`；`AutoSetup=0x57c9a60–0x57ca360`（0x900 B）。

两个样本的地址不同，**Evidence 不能混用**：同一条伪代码结论必须绑定对应的 SHA-256。Go 1.26.10 是用官方 `go.mod`/CI 基线重建的校准样本；Go 1.27.3 是实际构建产物。Go 1.25 原样无法编译当前源码，原因见 4.2。

#### 2.2 目标函数：`AuthHandler.AutoSetup`

目标选桌面端的自动初始化/登录入口：

- 源码位置：`internal/handler/auth.go:899`（仅用于校准，真实项目不依赖源码）。
- 二进制行为：检查 `Edition == "lite"`；校验 `X-WeKnora-Desktop-Token`；查找或创建默认用户 `admin@weknora.local`；生成随机密码/用户名；签发 token；返回 200。
- 选它的理由：它同时覆盖“版本开关、请求头常量、服务接口调用、随机数、错误码、响应渲染”，适合练习函数级证据。

目标不是整个 `handler` 包，也不是整个认证链路；只回答这个函数的控制流和调用点。

#### 2.4 与第 3 章 Evidence 的引用关系

第 3 章报告的是**文件级事实**，第 4 章报告的是**函数级事实**；两者不是替代关系，引用时必须绑定同一个 SHA-256。

| 第 3 章报告 | evidence_id / 命令 | 建立的事实 | 第 4 章怎么用 |
|---|---|---|---|
| `inspect-artifact` | `ev_df090734…24885` | 样本 SHA-256、格式、容器图 | 绑定第 4 章 Evidence 的 `subject.digest.sha256`；不同 SHA 不能互引 |
| `inspect-binary-layout` | `ev_05678e09…a4b7c82` | ET_EXEC、image base `0x400000`、`.text`/`.go.module` 节区、符号/重定位 | 校验 `moduledata.text`/函数 VA 落在 `.text`；确认 Ghidra 装载模型地址与 ELF 坐标 |
| `inspect-elf-notes` | `ev_5bb7e834…` | build-id、ABI note、Go note | 跨样本/构建识别；确认分析对象是哪一个构建 |
| `go version -m`（非 Evidence） | `/root/weknora-lite/WeKnora-Lite-go-version-m.txt` | Go 1.27.3、tags、依赖、`Edition=lite` | 解释 Ghidra 12.1.4 的 GoRttiMapper 版本门；决定是否重建 1.26.10 基线 |
| `inspect-go-binary` | 仅 ≤256 MiB；本样本未用 | 结构化 buildinfo | 大文件改用 `go version -m`；不要裁切 |

引用链示例（Go 1.27.3 样本）：

1. 第 3 章 `ev_df090734…` 给出样本 SHA `f748a597…e267aa16`；
2. 第 3 章 `ev_05678e09…` 确认 `.text` 为 ET_EXEC、image base `0x400000`，且 `.go.module` 存在；
3. 第 4 章从 `.go.module` 读 `moduledata.text=0xf0ea00`，加 `entryOff=0x47f4460` 得 `AutoSetup=0x5702e60`；
4. 第 4 章定向反编译得到行为结论；但该定向输出是 REA 外部流程，不是 REA provider Evidence；
5. 第 4 章全量尝试是 `provider_timeout`，没有 provider Evidence，不能引用。

引用规则：

- **先比 SHA**：第 3 章报告只适用于同 SHA 的样本；1.26.10 基线样本没有第 3 章报告，不能用 1.27.3 的 `ev_df09…` 代替。
- **文件级 vs 函数级**：第 3 章给节区/notes/构建，第 4 章给函数边界/伪代码/调用；拼成一条证据链时，分别标注 evidence_id 和坐标。
- **地址坐标**：ET_EXEC 的 image base 是 `0x400000`；Ghidra 报告装载模型地址；函数 VA 用 `moduledata.text + entryOff` 计算，并用第 3 章的 `.text` 范围校验。
- **不要跨对象**：第 3 章的 buildinfo/notes 不是函数级 Evidence；第 4 章 demo 的 `ce76…` Evidence 也不能引用到 WeKnora 样本。

### 3 全量自动分析（默认入口）

主流工具在第一遍都会尽量把函数、字符串、引用和调用关系建起来；这一步失败或不可用时，才进入定向后备。

#### 3.1 标准全量路径

Ghidra 在导入/新增程序时会自动运行 Auto Analysis；Ghidra 官方帮助列出的 Auto Analyzer 包括函数识别、栈分析、函数签名、参数 ID、字符串等，且可以用 `Analyze All Open` 对多个打开的程序统一分析。REA 的 `analyze`/`function`/`decompile` 会先触发完整导入+分析，再返回概览或函数 dossier。

```bash
rea analyze /path/to/app --provider ghidra --json
rea function /path/to/app --procedure main.call --provider ghidra --json
rea decompile /path/to/app --procedure main.call --provider ghidra --json
```

本次用 `/bin/ls` 冒烟：`rea analyze /bin/ls --provider ghidra --json` → **17.4 s**；概览约 650 个函数、近 500 个字符串、33 个段，Evidence `ev_e909a105…`。

正常流程就是：

```text
导入 → Auto Analysis（全量）→ 函数/字符串/调用图
     → function/decompile 目标函数 → 注释/类型 → 报告
```

Go 1.25 接口 demo 就是按这条路径做的；全量结果见 7.1：函数名、具体方法签名、直接调用和 itab 关系都能恢复。

#### 3.2 279 MB 样本的全量实测

Go 1.26.10 样本，`REA_GHIDRA_STARTUP_TIMEOUT_MS=3600000`（60 分钟），禁用之前触发 repair 风暴的 6 个分析器并 seed `AutoSetup`：

| 耗时 | 阶段/事件 |
|---|---|
| 0 | `ANALYZING all memory and code` |
| 8m29s | `GoRttiMapper: Untested Go version [1.26.10]`；`Missing bootstrap`；`GolangStringAnalyzer` 失败 |
| ~12m | `DecompileCallback` |
| 18–53m | `OperandReferenceAnalyzer`（约 35 分钟） |
| ~53m | `ConstantPropagationAnalyzer` |
| 60m | `provider_timeout`；`rea function` exit=1，elapsed=**3603s**，无 OOM |

其他观测：

- `Repairing body` 计数为 0（禁用预设生效）；错误 JSON 1.1 MB；Ghidra 临时日志随容器清理，stdout 另存 `full-go126-ghidra-stdout.log`（约 0.5 MB，尾部截断）。
- Go 1.27.3 样本在 30 分钟预算下就停在 `OperandReferenceAnalyzer`；默认分析器会产生 5,655 次 `Repairing body`，禁用后修复循环归零，但仍超时。
- 结论：**279 MB CGO + Ghidra 12.1.4 全量分析当前不可行**；这是当前对象/引擎的受阻，不是“全量不值得”。全量仍是默认流程；受阻时才用 6.4 的定向后备。

**这次全量没有生成成功的 provider Evidence**：超时返回的是 `provider_timeout` 错误信封（`code/category/message/retryable/remediation/recovery/details`），文件 `/root/weknora-lite-go126/full-go126-function.json` 没有 `evidence_id`、`records` 或 `manifest`，不能当 Evidence 或 bundle 引用。Go 1.27.3 的全量尝试同样超时；定向 `-noanalysis` 日志是 REA 外部流程，也不是 REA provider Evidence。

### 4 函数识别与符号恢复

全量分析之后（或全量不可用时），下一步是确认函数名、边界和真实地址。Go 二进制的身份主要来自 pclntab、moduledata、RTTI/API snapshot 和 GoReSym 一类工具。

#### 4.1 pclntab、moduledata 与函数地址

Go stripped 二进制仍保留 `pclntab`（函数名、入口偏移、行号表），但 **Go 1.26 起（1.26.0+）pclntab 不再保存 `textStart`**：该字段变成占位 `_ uintptr`，函数入口是相对 `moduledata.text` 的偏移。地址公式：

```text
函数 VA = moduledata.text + entryOff
```

本次两个样本的关键字段：

| 样本 | `.text` 起始 | `moduledata.text` | AutoSetup entryOff | AutoSetup VA |
|---|---|---|---|---|
| Go 1.27.3 | `0xacb340` | `0xf0ea00` | `0x47f4460` | `0x5702e60` |
| Go 1.26.10 | `0xaca340` | `0xf0da00` | `0x48bc060` | `0x57c9a60` |

`.text` 起始不能直接当 Go 代码基址：这两个 CGO 二进制的 Go 文本前还有 C/C++ 代码。用 `.text` 起始解析 pclntab 会把地址算低；`go tool addr2line` 在 stripped CGO 二进制上也可能受此影响。**以 `.go.module` 里的 `moduledata.text` 为准**。

本次用 pyelftools 读取 `.gopclntab` 和 `.go.module`；1.26/1.27 的 `moduledata` 布局一致，`text` 在偏移 `0xb0`、`etext` 在 `0xb8`。其他 Go 版本要按 `runtime/symtab.go` 的 `moduledata` 字段顺序核对，不能照搬偏移。

**名称解析**

| 名称 | 含义 |
|---|---|
| pclntab | Go 的 PC-行号/函数表；保存函数名、入口偏移、行号映射。 |
| moduledata | Go 运行时模块元数据；其中的 `text` 是 Go 代码真实基址。 |
| textStart | 旧版 pclntab 里的 Go 代码基址字段；Go 1.26 起已移除。 |

#### 4.2 RTTI、GoRttiMapper 与 API snapshot

Ghidra 的 Go 分析器除了 pclntab，还会读 RTTI/类型元数据来恢复类型、接口方法签名和字符串。`GoRttiMapper` 的受测区间是 `1.15-1.25`；Go 1.26.10/1.27.3 会报：

```text
ERROR (GoRttiMapper) Untested Go version [1.26.10]
WARN  (GoRttiMapper) Missing Go bootstrap type info, unable to extract Go RTTI info.
ERROR (GolangStringAnalyzer) Go string analyzer error: unable to get GoRttiMapper
```

社区进展：

- Ghidra #9013：Go 1.26 同样报 `Missing Go bootstrap type info`；根因是 `SUPPORTED_VERSIONS`、`moduledata` 迁到 `.go.module`、新增 `epclntab` 字段。已在 **Ghidra 12.2**（2026-10-22）修复，并随包提供 `go1.26.0.json`。
- Ghidra #9219：Go 1.26 在 `GoUncommonType` 触发 `EOFException`，已关闭。
- 截至 2026-10-28，Ghidra 12.2 只提供到 `go1.26.0.json`，**没有 Go 1.27 快照**；GitHub 上也没有 Go 1.27 的 Ghidra issue。
- GoReSym v3.4.1 的备用布局只尝试 1.20–1.26；Go 1.27 支持 issue #90 仍 open，不能假设它能解析 1.27。
- Ghidra 12.2 要求 JDK 25（`application.java.min=25`）；当前镜像只有 JDK 21，因此 12.2 暂未启用。
- Go 1.25 不是干净的替代：1.25.14 仍有 pclntab `textStart`，但当前源码有 6 个依赖声明 `go 1.26`（`weaviate*`、`chromedp*`、`ollama`、`go-json-experiment/json`）。降根 `go.mod` 到 1.25 + `GOTOOLCHAIN=local` 会报 `chromedp/cdproto requires go >= 1.26`；不设 `local` 则自动切到 `go1.26.0`。要得到 1.25 只能降级/替换这 6 个依赖，产物不再代表当前源码。

RTTI 只负责 Go 类型/字符串注解，函数边界和名字可以来自 pclntab + `moduledata.text`；定向反编译不依赖 RTTI。GoReSym 可以离线解析 pclntab/moduledata 并输出函数名/地址/源码路径，再用 Ghidra/IDA 脚本重命名；它适合作为全量分析前的符号恢复预处理器。

**名称解析**

| 名称 | 含义 |
|---|---|
| RTTI | 运行时类型信息；与 buildinfo、pclntab 不是一回事。 |
| GoRttiMapper | Ghidra 里把 Go RTTI/类型元数据映射成程序模型的组件。 |
| API snapshot | Ghidra 随包提供的 Go 版本 API/类型快照（如 `go1.26.0.json`）。 |
| GoReSym | Mandiant 的 Go 符号恢复工具；解析 pclntab/moduledata，输出函数/类型/路径。 |

### 5 目标选择与 triage

全量分析完成后，不要逐个函数读；按入口、导入、字符串、xref 和调用图筛选高价值函数。

#### 5.1 概览分析（`analyze`）

```bash
rea analyze /path/to/app --provider ghidra --json
```

本次 `/bin/ls` 冒烟 17.4 s，约 650 个函数、近 500 个字符串、33 个段，Evidence `ev_e909a105…`。概览只负责“第一眼”，不替代函数级 dossier。

#### 5.2 源码只做 ground truth

教程用开源 WeKnora，是因为它有 commit `97d7f0a` 的源码，可以当“标准答案”校准反编译结果；这不代表真实项目可以拿源码做分析前提。真实项目应按二进制证据推进：

| 信息 | 教程校准（开源） | 真实项目（只有二进制） |
|---|---|---|
| 函数身份 | 源码函数名/行号 | pclntab、RTTI/API snapshot、GoReSym |
| 行为 | 源码语句 | 伪代码控制流、字符串、错误码、调用顺序 |
| 接口具体实现 | 源码依赖注入/构造 | itab + wrapper + 具体方法；必要时动态验证 |
| 参数名 | 源码声明 | 通常不可恢复；只能按语义命名并标 inferred |

本章的命令仍可用源码辅助理解，但结论必须能回到二进制证据；不能把“源码里是这么写的”当作 observed。

#### 5.3 字符串、名称、xref 与调用图

社区常见 triage 顺序是：先找可搜索的线索，再连到代码，再重建调用关系，最后只反编译相关函数。

```bash
rea trace /path/to/app "literal-query" --provider ghidra --json
rea xrefs /path/to/app --address <address-or-symbol> --provider ghidra --json
```

本次目标 `AutoSetup` 的选择依据：

- 字符串/行为：`auto-setup is only available in lite edition`、`X-WeKnora-Desktop-Token`、`admin@weknora.local`、`user_%s`。
- 调用关系：`gin.Context.Error/Render`、`logger.Info/Errorf`、`dto.NewAuthLoginResponse`。
- 入口/路由：桌面端 `/api/v1/auth/auto-setup` 的 handler。

`xrefs`/`trace` 是“线索”，不是完整调用图：同一字符串可能被多个函数引用；间接调用和接口分派可能缺失。

#### 5.4 命令与选择器

```bash
rea function /path/to/app --procedure <name> --provider ghidra --json
rea function /path/to/app 0x57c9a60 --provider ghidra --json
rea decompile /path/to/app --procedure <name> --provider ghidra --json
rea decompile /path/to/app 0x57c9a60 --provider ghidra --json
```

选择器要点：

- 以 `-` 开头的值用等号：`--procedure=`、`--pattern=`；`xrefs` 的地址用 `--address=`。
- `function`/`decompile` 的地址用**位置参数**（如 `rea function <path> 0x57c9a60`），不接受 `--address`。
- Ghidra 地址可带/不带 `0x`，支持 `EXTERNAL:0x1`。
- 显式地址/地址空间优先；否则精确符号名优先于裸十六进制。

> `function`/`decompile` 会触发 Ghidra 的完整导入+分析，这是正常流程；279 MB 样本当前会耗尽启动预算，见 3.2。全量受阻时才走 6.4 的定向后备。

### 6 函数级反编译

全量分析完成后，对选中的函数做反编译；主流做法是伪代码和汇编对照，结合调用者/被调用者，边读边重命名/注释。

#### 6.1 标准入口：全量分析 + `function`/`decompile`

```bash
rea function /path/to/app --procedure main.call --provider ghidra --json
rea decompile /path/to/app --procedure main.call --provider ghidra --json
```

`function` 返回函数 dossier（伪代码、汇编、调用者/被调用者、引用、基本块等）；`decompile` 只返回伪代码，适合快速确认。Go 1.25 demo 的全量结果见 7.1：函数名、具体方法签名、直接调用和 itab 关系都能恢复。

在 279 MB 的 WeKnora-Lite + Ghidra 12.1.4 + Go 1.26/1.27 上，全量会耗尽启动预算（3.2）；此时不要重复同一个超时调用，改用 6.4 的定向后备。

#### 6.2 读伪代码

Ghidra 输出的是 C-like 伪代码，不是原始 Go 源码。结合本次 `AutoSetup` 的片段，先认识几类噪声：

| 伪代码片段 | 实际含义 |
|---|---|
| `while (&iStack_f8 <= *(int **)(unaff_R14 + 0x10)) { FUN_00fa3c00(); }` | Go 的栈增长检查（`CMP SP, 16(g)` + `morestack`）；源码里没有这个 `while`。`unaff_R14` 是未被建模的 g 寄存器。 |
| `FUN_00fa3c00()` | `runtime.morestack_noctxt`（callee 表已确认）。 |
| `FUN_*` | 未恢复的调用；用 callee 表、xrefs 或源码对照确认身份。 |
| `iStack_*`、`uStack_*`、`extraout_*` | 反编译器推断的栈槽/寄存器残值，不是源码变量名。 |
| `param_1`、`param_2` | Ghidra 猜的函数签名；Go 的 receiver/参数走寄存器，名字不可得。 |
| `DAT_*`、`PTR_DAT_*` | 全局/字符串/类型元数据；按地址读字节确认内容。 |
| `puVar3[2] = 0x2c; puVar3[1] = &DAT_0912401e; puVar3[5] = 0x193;` | 错误对象的消息长度 44、字符串 `auto-setup is only available in lite edition`、HTTP 403。 |

`AutoSetup` 的 lite 检查在伪代码里是：

```c
if ((DAT_1070ef38 != 4) || (*(sdword *)PTR_DAT_1070ef30 != 0x6574696c)) {
    puVar3 = ...;
    puVar3[2] = 0x2c;
    puVar3[1] = &DAT_0912401e;
    puVar3[5] = 0x193;
    FUN_01931ca0(..., &PTR_DAT_0b53ba80, puVar3);
    return;
}
```

逐项读：`DAT_1070ef38 != 4` 是 Edition 字符串长度；`0x6574696c` 是小端 “lite”；`DAT_0912401e` 是错误串；`0x193` 是 403；`FUN_01931ca0` 是 `gin.Context.Error`。

#### 6.3 与源码对照（校准）

用源码 `internal/handler/auth.go:899` 做 ground truth，对比 Go 1.26.10 定向伪代码：

| 源码行为 | 伪代码/二进制证据 | 判断 |
|---|---|---|
| `Edition != "lite"` → 403 | 长度 4 + `0x6574696c`（“lite”），错误串 `auto-setup is only available in lite edition` | 一致 |
| `liteSetupToken` 为空或 header 不匹配 → 401 | 长度检查 + `MIMEHeader.Get`（长度 `0x17`，`X-WeKnora-Desktop-Token`）+ 逐字节 XOR 累加，错误串 `desktop authentication is required` | 一致（`ConstantTimeCompare` 被内联） |
| 默认邮箱 `admin@weknora.local` | 字符串长度 `0x13`，内容确认 | 一致 |
| `GetUserByEmail`，user 为 nil 时创建 | 接口调用 `*param_1+0x68`，nil 分支进入创建流程 | 调用点一致；接口身份为推断 |
| `rand.Read` 24 字节 + base64 + `user_%s` | `crypto/rand.Read` 0x18；两次 `EncodeToString`（24 和 6 字节）；`fmt.Sprintf` 格式串 `user_%s` | 一致 |
| `Register` 失败 → logger + 500 | 接口调用 `*param_1+0xc0`；日志串 `Auto-setup: failed to register default user: %v`；错误 `auto-setup failed` | 一致 |
| 注册后再次 `GetUserByEmail`，仍 nil → 500 | 第二次 `+0x68` 调用；错误串 `auto-setup failed: user not found after registration` | 一致 |
| `GenerateTokens` 失败 → logger + 500 | 接口调用 `*param_1+0x40`；日志串 `Auto-setup: failed to generate tokens: %v` | 调用点一致；接口身份为推断 |
| `GetTenantByID(ctx, user.TenantID)` | `param_1[2]+0x30`，参数取 `user+0x50` | 结构匹配；身份为推断 |
| 最后 logger + `dto.NewAuthLoginResponse` + 200 | `logger.Info`、`dto.NewAuthLoginResponse`、`gin.Context.Render(200)`；响应 `Message = "Auto-setup successful"` | 一致（`c.JSON` 内联成 `Render`） |

结论：**控制流、错误码、字符串常量和服务调用顺序与源码一致，未发现语义矛盾**；但不能声称“逐行/逐指令等价”。接口调用的具体身份（`+0x68`/`+0xc0`/`+0x40`/`+0x30`）是按源码调用顺序和参数推断的，不是 Ghidra 恢复的符号名；伪代码里的 `extraout_*`、`in_stack_*` 和寄存器 ABI 也不能当作逐指令证据。

#### 6.4 全量受阻时的定向后备

本次用 Ghidra 12.1.4 的 `analyzeHeadless` 导入完整文件，但加 `-noanalysis` 跳过全量分析；脚本按 `moduledata.text + entryOff` 的地址反汇编目标函数，创建函数，并用 `DecompInterface` 只反编译它。直接 callee 用 pclntab 函数表补建。

Go 1.26.10 样本的命令形态：

```bash
analyzeHeadless /tmp/proj rea \
  -import /data/WeKnora-Lite -noanalysis \
  -processor "x86:LE:64:default" -cspec golang \
  -scriptPath /data/ghidra-scripts \
  -postScript TargetDecompile.java \

```

结果：

- Go 1.27.3 样本：`0x5702e60–0x57037c0`，16 个直接 callee。
- Go 1.26.10 样本：`0x57c9a60–0x57ca360`，15 个直接 callee；含 `runtime.convT/newobject/morestack/gcWriteBarrier`、`fmt.Sprintf`、`crypto/rand.Read`、`encoding/base64`、`net/textproto.MIMEHeader.Get`、`gin.Context.Error/Render`、`logger.Info/Errorf`、`dto.NewAuthLoginResponse`。

> 这条路径绕开了 REA 的 Ghidra provider，输出不是 REA Evidence；引用时要标注“工具级观察”，并保留命令、样本 SHA、脚本和日志。它只用于“全量已经失败、只差单函数控制流”的场景，不是默认入口。

#### 6.5 注释、重命名与引用追踪

社区做法是边读边把名字/类型/注释写回分析数据库，并用调用者/被调用者确认上下文；不要孤立地读一个函数。

```bash
rea xrefs /path/to/app --address <address-or-symbol> --provider ghidra --json
rea trace /path/to/app "literal-query" --provider ghidra --json
```

- 用 `procedure_callers`/`procedure_callees`/`get_call_graph` 确认上下文；接口调用还要看 7.1 的 itab/wrapper 链。
- Ghidra 的注释/重命名属于临时分析数据库；关闭/取消会丢失。需要保留时，把结论写进 Evidence/报告，或在关闭前导出快照（如果 provider 支持）。
- 伪代码和汇编要对照看：类型、调用约定、栈帧和寄存器 ABI 的细节以汇编/指令为准。
- 同一字符串可能被多个函数引用；字符串搜索是线索，不是调用图。

### 7 类型、接口与间接调用

具体方法/类型通常能通过 RTTI/API snapshot 恢复；接口 dispatcher 的目标需要顺 itab/wrapper 走，或者动态确认。

#### 7.1 全量能力实例：Go 1.25 接口 demo

用 Go 1.25.14 + Ghidra 12.1.4 构建一个 1.5 MB 的 stripped demo，按正常全量流程分析：

```go
type Greeter interface { Greet(string) string }
type English struct{}

//go:noinline
func (English) Greet(name string) string { return "hello " + name }

//go:noinline
func call(g Greeter, name string) string { return g.Greet(name) }

//go:noinline
func main() { fmt.Println(call(English{}, "world")) }
```

| 对象 | 结果 |
|---|---|
| `main.English.Greet` | ✅ 恢复为 `main::main.English.Greet`；`Golang signature [from_rtti_method]: func (English) Greet(string) string`；参数 `self: main.English`、`param_2: string`，置信度 high |
| `main.main` | ✅ 直接调用 `main::main.call`；带源码行号 |
| `main.call` 的接口调用 | ❌ 仍是 `(**(code **)(...+0x18))(...)`；`unresolved_calls` 一条；callee 中没有 `English.Greet` |
| `main.call` 的类型/参数 | ❌ `signature = undefined main.call()`；参数是 `int`/`undefined8`，置信度 low；只能看到 `Golang stacktrace signature: func main.call(struct? {8, 8}, struct? {8, 8}) ???` |
| 接口类型名 | ❌ 没有恢复出 `Greeter`；只看到底层的 `internal_abi_Type`/接口结构 |

本次主观评分（仅这个 demo）：

| 项目 | 评分 | 说明 |
|---|---|---|
| 函数识别/命名 | 9/10 | 函数名、行号完整 |
| 具体方法签名/类型 | 9/10 | RTTI 方法签名 high |
| 接口实现关系 | 8/10 | itab 符号直接给出，调用目标需人工跟 |
| 直接调用图 | 9/10 | 直接调用正确 |
| 接口目标自动标注 | 4/10 | dispatcher 仍是间接调用 |
| 接口函数参数类型 | 3/10 | 只见两个 8 字节结构 |
| 参数名 | 1/10 | stripped 二进制没有 DWARF |
| 伪代码可读性 | 6/10 | 栈检查、`iStack/uStack` 噪声 |
| 无源码行为重建 | 8/10 | 能推出 `hello world` 行为 |

接口 dispatcher 的目标需要“顺 itab 走一步”：amd64 的 `itab + 0x18` 是 `Fun[0]`。本次 demo 的链路：

| 项 | 值 |
|---|---|
| itab 地址 | `0x4e46f8` |
| `itab + 0x18` | `0x4e4710` |
| 读出的 `Fun[0]` | `0x498620` |
| `0x498620` | `main.(*English).Greet`（指针接收者 wrapper） |
| wrapper 的 callee | `main.English.Greet` |

因此 `main.call` 的接口调用目标可以还原为 `English.Greet`。多方法接口的 `Fun[i]` 按接口方法表顺序（通常按方法名排序），不是源码声明顺序；itab 地址、`Fun[i]` 指针、wrapper、具体方法是 observed，`Fun[i] -> 方法名` 未核对接口方法表时标 inferred。

完整的 REA/Ghidra 操作（`list_names`/`read_bytes`/`procedure_info`/`procedure_callees`）、找不到 itab 符号时的回溯、devirtualize/nil/多层 wrapper 处理，见“接口目标追踪（itab）”实践记录。

### 8 证据边界与报告

函数级结论要带 provider 边界、样本 SHA 和坐标说明：Ghidra 报告的是装载模型地址，与 ELF 表级坐标不同；需要表级事实时回到第 3 章。第 3 章 Evidence 的引用方式见 2.4。

动态验证是证据边界的一部分：它能补上实际实现/值和运行时分支，但不能恢复参数名。

#### 8.1 动态验证边界

静态分析能给出控制流、字符串、调用点和部分类型；运行时才能确认实际绑定到哪个实现、实际走哪条分支、参数值是什么。

| 信息 | 静态全量 | 动态调试/插桩 | 源码 |
|---|---|---|---|
| 接口具体实现 | 需要 points-to/itab 分析，通常仍 unresolved | 能看到实际 concrete type/itab | 可看依赖注入/构造 |
| 类型/方法签名 | RTTI/API snapshot 可恢复具体方法 | 能看到运行时类型 | 明确 |
| 参数名/语义 | stripped 后基本拿不到 | 也拿不到名字，只能看到值 | 唯一可靠来源 |
| 参数值/分支结果 | 常量、字符串、错误码可推断 | 能看到实际值 | 明确 |

所以“解析具体参数名和含义”不是动态调试的任务：参数名本来就不在 stripped 二进制里；动态是用来回答“实际绑定到哪个实现、走哪条分支、值是什么”。本章不运行目标；运行时验证见第 5 章。

#### 8.2 能证明什么

- 函数边界、控制流、错误码、字符串常量、直接调用顺序。
- 在给定样本 SHA 下，本次 `AutoSetup` 的伪代码与源码校准结果一致（控制流/错误码/字符串/调用顺序）。
- 具体方法签名（引擎支持该 Go 版本、RTTI 可用时）和 itab 关系。
- 定向反编译的直接 callee 列表（由 pclntab 地址表补建）。

#### 8.3 不能证明什么

- 接口 dispatcher 的具体实现，除非顺着 itab/wrapper 走完；否则只能标 inferred/unknown。
- 源码参数名和完整类型：stripped Go 二进制通常没有 DWARF；动态调试也拿不到名字。
- 函数间的完整调用图：间接调用、接口分派、CGO/回调都可能缺失。
- 运行时行为、实际分支值、数据库写入：需要第 5 章以后的动态验证。
- “全量分析已完成”：在 279 MB + Ghidra 12.1.4 上当前是 `provider_timeout`，不能声称覆盖完整。

#### 8.4 observed / inferred / unknown 示例

| 结论 | 等级 | 依据 |
|---|---|---|
| `Edition == "lite"` 检查 | observed | 长度 4 + `0x6574696c` + 错误串 |
| `X-WeKnora-Desktop-Token` 与 `liteSetupToken` 的常量时间比较 | observed | `MIMEHeader.Get` + XOR 累加 + 401 错误串 |
| `admin@weknora.local`、`user_%s`、24 字节随机密码 | observed | 字符串内容/长度 + `crypto/rand.Read`/`base64`/`fmt.Sprintf` |
| `GetUserByEmail`/`Register`/`GenerateTokens`/`GetTenantByID` 的接口身份 | inferred | 调用顺序、参数偏移、源码校准；不是 Ghidra 符号 |
| 接口实际绑定的具体实现 | unknown | 需要 itab/wrapper 追踪或动态验证 |
| 运行时实际 token、分支和数据库结果 | unknown | 未运行目标；留第 5 章 |

#### 8.7 Provider 边界

| Provider | 边界 |
|---|---|
| Ghidra | 临时数据库；取消会销毁临时库并丢注释；启动超时默认 330000 ms |
| Hopper | 调用关系完整性可能 unknown；不会全二进制反扫 |
| IDA | 只读；不保存/关闭已打开的 GUI 数据库 |
| Windows P0 | 只读，无 mutation authority |

> 定向 `-noanalysis`、`analyzeHeadless` + `TargetDecompile.java` 是 REA 外部流程，不是 REA provider Evidence；引用时要记录命令、样本 SHA、脚本和日志。

### 9 练习与复现

1. 在容器内跑 `rea doctor --provider ghidra --json`，确认 healthy（镜像已装 Ghidra 12.1.4 + JDK 21）。
2. 选一个小二进制（不要用 279 MB 的 WeKnora-Lite）跑 `rea analyze`，记录函数/字符串/段计数。
3. 对两个 WeKnora-Lite 样本读 `.go.module` 的 `moduledata`：确认 1.27.3 的 `text=0xf0ea00`、`AutoSetup=0x5702e60`；1.26.10 的 `text=0xf0da00`、`AutoSetup=0x57c9a60`。用 `.text` 起始对照，理解地址差。
4. 对 Go 1.25 接口 demo 跑全量分析，记录：具体方法签名、直接调用、接口 dispatcher、itab/wrapper 链各恢复到什么程度。
5. 对 WeKnora 样本，因为全量受阻，用 `-noanalysis` 定向反编译 `AutoSetup`，在伪代码里找出 3 个行为：`Edition == "lite"`、`X-WeKnora-Desktop-Token` 常量时间比较、`admin@weknora.local` + `gin.Context.Render(200)`；核对 15/16 个直接 callee，并注明这是后备而非默认入口。
6. （可选）对 279 MB 样本跑 60 分钟全量分析，记录 `provider_timeout` 的阶段时间线；不要重复未改变的超时调用。
7. 写 3 条 observed、2 条 inferred、2 条 unknown，并注明“定向后备不属于 REA provider”和“全量分析超时”两个边界。
8. （可选）把 demo 的 Evidence 导出为 bundle，再导入/导出一次，核对 records 数和 SHA-256。
