### 3 什么时候用 REA

| 问题 | 推荐工具 |
|---|---|
| 这个文件是什么格式、架构、摘要？ | `rea inspect-artifact` |
| 这个 Go 二进制用什么 Go/依赖构建？ | `rea inspect-go-binary` |
| 某个函数大概做什么？ | `rea function` / `rea decompile`（需要 provider） |
| 这个 CLI 运行时会输出什么、会不会写文件？ | `rea capture-process` |
| 这个网页/Electron 应用加载了什么脚本？ | JS/Electron 静态分析、浏览器场景 |
| 我该让 agent 怎么调查？ | MCP prompts + tool catalog |

**名称解析**

| 名称 | 含义 |
|---|---|
| MCP | Model Context Protocol，agent 调用外部工具的协议；REA 通过 stdio/HTTP 暴露工具。 |
| Evidence | 观察 + 来源 + 覆盖 + 限制 + unknown 的结果封装。 |
| provider | 实际执行分析的引擎/适配器；REA 负责编排和 Evidence。 |
| tool / prompt | tool 是原子能力；prompt 是引导 agent 调查的工作流。 |
| Electron | 用 Chromium + Node.js 构建的桌面应用运行时。 |

### 4 从源码到进程

Java 开发者熟悉的链路是：

```text
.java -> javac -> .class -> JAR -> JVM 类加载 -> JIT/AOT -> 进程
```

原生程序的链路类似，但产物形态不同：

```text
C/C++/Go/Rust 源码
  -> 编译器（gcc/clang/go/rustc）
  -> 目标文件（.o）
  -> 链接器（ld/lld）
  -> 可执行文件（ELF/PE/Mach-O）
  -> 加载器（ld.so / Windows loader / dyld）
  -> 进程（代码段、数据段、堆、栈、共享库）
```

关键区别：

- Java 字节码面向 JVM，指令集和对象模型由 JVM 规定；原生程序直接面向 CPU 指令集和操作系统 ABI。
- Java 的类加载器在运行时解析类；原生程序的动态链接器在加载时解析共享库和符号。
- Java 的 JIT 在运行时生成代码；原生程序通常由 AOT 编译器提前生成机器码。
- Java 的 `javap` 能看到字节码；原生程序需要反汇编器（objdump/Rizin/Ghidra/IDA）才能看到机器码。

### 5 二进制里到底有什么

| 概念 | 含义 | Java 类比 |
|---|---|---|
| container | 文件/打包容器（ELF、PE、Mach-O，或 APK、ASAR、PCK 等）；本文的“容器”不指 Docker | JAR/WAR/APK 等产物封装 |
| section / segment | 代码、只读数据、可写数据、调试信息等分区 | class 文件的常量池/方法表等结构 |
| note | ELF 的元数据表（`PT_NOTE`/`SHT_NOTE`），常见 build-id、ABI tag、Go note | `MANIFEST.MF` 中的构建/签名属性（不精确类比） |
| symbol | 函数/变量名及地址 | 方法名/字段名 |
| import / export | 依赖外部库的符号 / 对外提供的符号 | 依赖的类/包、公开 API |
| relocation | 链接/加载时需要修正的地址引用 | 运行时的符号解析/重定位 |
| PLT / GOT | 动态链接的跳转表/全局偏移表 | 动态代理/方法分派表（不精确类比） |
| PIE / ASLR | 可执行文件随机基址 / 地址空间随机化 | 对象地址每次运行不同 |
| debug info | 源码文件、行号、类型、变量信息 | 调试符号/行号表 |
| stripped | 符号表被移除，函数名/调试信息减少 | 混淆/去掉方法名（不精确类比） |

这些概念决定了：

- 为什么反编译输出里的函数名可能是 `FUN_00123456`；
- 为什么 `xref` 能告诉你“谁调用了这个地址”；
- 为什么同一个二进制在不同基址下地址会变化；
- 为什么 `stripped` 会让分析成本显著上升；
- 为什么 `pclntab` 对 Go 二进制特别重要。

### 6 读机器码的最小知识

不需要成为汇编专家，但要知道：

1. **寄存器**：CPU 的工作变量；x86-64 常见 `rax/rbx/rcx/rdx/rsi/rdi/rsp/rbp` 和 `r8-r15`。
2. **栈**：函数调用时保存返回地址、局部变量和参数；`rsp` 指向栈顶，`rbp` 常作帧指针。
3. **调用约定**：参数放在哪些寄存器、返回值放哪里、谁清理栈。Linux x86-64 常用 System V ABI；Windows x64 使用另一套。
4. **函数序言/尾声**：`push rbp; mov rbp, rsp; ...; leave; ret` 这类模式可以帮助识别函数边界。
5. **地址**：反编译输出里的地址是虚拟地址；需要和文件偏移、基址、ASLR 区分。
6. **控制流**：条件跳转、循环、switch/jump table；CFG 是这些边的图。
7. **数据流**：值从哪来、到哪去；REA 的 `trace_native_values` 就是把 def-use 关系抽出来。

读反编译输出时，优先问：

- 这个函数的输入参数是什么？
- 它返回什么？
- 它调用了哪些外部函数/系统调用？
- 它访问了哪些全局数据/字符串？
- 哪些分支对应错误处理/权限检查？

### 7 静态分析：反汇编与反编译

| 层 | 输入 | 输出 | 典型工具 |
|---|---|---|---|
| 反汇编 | 机器码 | 汇编 | objdump、Rizin、Ghidra、IDA |
| 反编译 | 汇编/IR | 伪代码 | Ghidra、IDA/Hex-Rays、Hopper |
| IR/P-code | 指令语义 | 中间表示 | Ghidra P-code |
| CFG | 基本块/跳转 | 控制流图 | Ghidra、IDA、Rizin |
| xref | 引用关系 | 谁引用谁 | Ghidra、IDA、Rizin、REA |

关键经验：

- 反编译不是“还原源码”，而是“生成可读的近似表示”；类型、变量名、控制流都可能不准确。
- 先看字符串、导入表、符号和调用关系，再决定反编译哪个函数；不要从入口一路硬读。
- `stripped` 后先找字符串/导入/间接调用，再考虑函数聚类和签名匹配。
- 静态分析不证明运行时行为；它只证明“文件里存在这些字节/结构”。

### 8 动态分析：调试与运行时观察

| 手段 | 你能看到什么 | 代价/风险 |
|---|---|---|
| GDB | 断点、寄存器、栈、内存、调用栈 | Linux；需要 TTY；可能改变目标状态 |
| Rizin debug | 断点、寄存器、内存、反汇编、调试命令 | Linux；需要 TTY；目标可能继续运行 |
| Frida | 运行时插桩、函数 hook、参数/返回值 | 需要注入；可能被反调试；影响目标 |
| 进程捕获 | 终端输出、生命周期、文件系统观察 | 不是沙箱；以当前用户权限运行 |
| 浏览器/CDP | 页面结构、脚本、网络、截图 | 可能访问网络/改变页面状态 |

动态分析的核心是**有界实验**：

- 明确目标、输入、预期观察和停止条件；
- 使用隔离环境/测试数据；
- 记录命令、时间、环境和版本；
- 不把一次运行的结果当成所有路径的结论。

### 9 系统工程与工作流

逆向工程不是“打开工具随便看”，而是一个可复现的调查过程：

```text
问题
  -> 确认授权/范围
  -> 产物身份（版本、SHA-256、来源）
  -> 格式/架构/依赖盘点
  -> 静态线索（字符串、导入、符号、xref）
  -> 重点函数/CFG/反编译
  -> 动态验证（可选）
  -> Evidence 报告（observed / inferred / unknown）
```

系统工程经验：

1. **先定义问题**：版本？依赖？某个功能？某个协议？问题越具体，工具越少。
2. **固定输入**：记录文件 SHA-256、版本、构建时间；不要用“最新版”做对照。
3. **固定工具链**：记录 provider、版本、参数、插件；不同版本可能给出不同伪代码。
4. **隔离**：运行时分析用独立容器/虚拟机/测试账号；不要碰生产数据。
5. **可复现**：命令、输入、输出、证据 ID 都要能重放。
6. **区分事实等级**：observed / derived / inferred / unknown；不要把推断写成观察。
7. **保留 unknown**：没有覆盖不等于不存在；不要为了“完整”而猜。
8. **控制成本**：反编译大二进制很贵；先源码/字符串/导入，再函数级。
9. **最小权限**：只给分析所需的文件/网络/设备权限；不要默认 root/生产凭据。
10. **数据边界**：抓包、内存、日志可能含敏感数据；分享前脱敏/审查。

### 10 Java 开发者映射表

| Java 世界 | 原生/逆向世界 | 说明 |
|---|---|---|
| `.class` / JAR | ELF / PE / Mach-O / APK / ASAR | 产物容器不同，分析方法不同 |
| `javap -c` | objdump / Rizin / Ghidra 反汇编 | 看字节码 vs 看机器码 |
| CFR / Procyon / Fernflower | Ghidra / IDA / Hopper | Java 反编译 vs 原生反编译 |
| JDB / JDI / JVM TI | GDB / Rizin / ptrace | 调试接口不同 |
| JMX / Java Agent | Frida / 运行时插桩 | 运行时观测/修改 |
| JIT | AOT 编译器 | 运行时生成 vs 提前生成 |
| 异常栈 | unwind / debug info | 栈回溯机制不同 |
| ClassLoader | 动态链接器 / loader | 运行时解析依赖 |
| 反射 / 动态代理 | 间接调用 / PLT/GOT | 静态分析更难直接看到目标 |
| 方法签名 | 符号 / mangling / ABI | 名称恢复依赖符号/约定 |

这个映射不是一一等价，但能帮你把已有的 Java 调试/性能/排障经验迁移过来。

### 11 新手常见误区

- **反编译输出就是源码**：不是；类型、变量名、控制流都可能错。
- **字符串能代表逻辑**：字符串只是线索，必须回到引用点和调用链。
- **函数名一定可靠**：`stripped` 后可能是 `FUN_...`；Go 的 `pclntab` 能帮一部分。
- **一个 provider 的结果就是全部**：Ghidra/IDA/Hopper 可能给出不同伪代码；记录 provider 和限制。
- **静态分析能证明运行行为**：不能；需要动态验证。
- **没看到就等于不存在**：覆盖不完整时只能是 unknown。
- **跑通一次就能下结论**：需要可复现命令、输入和证据；一次成功不等于稳定。
